Identity & security

Users, groups and permissions

AWSIAM→AzureMicrosoft Entra ID + Azure RBACGCPCloud IAM + Cloud Identity

AWS IAM keeps users, groups and permission policies in one service. Azure splits it: Entra ID stores identities (users, groups, app registrations) and Azure RBAC grants roles at a scope (management group, subscription, resource group or resource). Google Cloud keeps one IAM policy per resource that binds principals (users, Google groups, service accounts) to roles; groups live in Cloud Identity or Google Workspace.

AWS

IAM group + managed and custom policies

aws iam ↗

AWS console

  1. Open IAM → User groups → Create group. Name grp-nextgen-platform-admins, attach PowerUserAccess (or narrower) → Create user group.
  2. Add members on the group's Users tab. With IAM Identity Center, create the group and a permission set there instead.
  3. Custom policy: IAM → Policies → Create policy → JSON, paste the document from the CLI block, name NextGenVmOperator, then attach it to the group.
  4. Pipelines: IAM → Identity providers → Add provider → OpenID Connect for Azure DevOps or GitHub, then a role that trusts it. No access keys are stored.

Neither cloud has an Internet Gateway object to create and attach. A VNet has a system route to the internet, and a GCP VPC gets a 0.0.0.0/0 route to the default internet gateway when it is created. What decides access is whether a resource has a public IP or a load balancer in front of it (inbound), and a NAT path (outbound, step 08). This step reserves the public IPs the load balancers use later.
